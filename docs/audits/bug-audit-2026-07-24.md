## Executive summary

This audit focused on API auth/ownership enforcement, messaging/RFQ access paths, discover/profile data exposure, and session/middleware edge cases.  
Two P1 issues were found: a contact-PII leak reachable by anonymous callers and a claim-verification token leak that can bypass email proof when delivery fails.  
A second tier of issues shows auth/abuse-control drift where route-layer checks exist but database RPC grants are broader than intended.  
The most urgent fixes are in SQL and claims route logic, not UI.  
No fixes were implemented in this pass (audit-only).

| REZ6-01 | P1 | Discover / supplier profile / PII | `buyer_supplier_profile` returns address `phone` + `email` and is executable by `anon`, enabling public PII extraction outside UI gating. | `supabase/migrations/0036_supplier_relationships.sql` (function `buyer_supplier_profile`, addresses JSON includes `phone` and `email`, grant to `anon`), `supabase/migrations/0024_buyer_supplier_profile_rpc.sql` (same exposure + grant), `app/(marketing)/suppliers/[slug]/page.tsx` (UI strips at render only). | Call Supabase RPC `buyer_supplier_profile` using anon key for any published slug; response includes `addresses[].phone` and `addresses[].email` even though marketing UI masks them. | Remove phone/email from RPC output for non-admin surfaces (or split RPCs by audience and revoke anon from sensitive shape). |
| REZ6-02 | P1 | Claims / verification | Production claim API can return `dev_verification_url` (contains raw token) whenever email sending fails, enabling verification-token bypass without inbox ownership. | `app/api/v1/claims/route.ts` (`includeDevUrl = NODE_ENV !== 'production' || sendResult.sent === false` then returns `dev_verification_url`), `lib/email/resend.ts` (explicit `sent:false` paths). | Trigger `claim_initiate` while provider send fails (`RESEND_API_KEY` missing/invalid/provider error); API response includes direct token URL; use token to call `verify` path and progress claim without email access. | In production, never return verification URL/token; fail request or queue retry when mail send fails. |
| REZ6-03 | P2 | Messaging / auth gap | `thread_open` RPC lacks buyer/admin role enforcement and is granted to all authenticated users, so supplier accounts can create buyer-side threads by calling RPC directly. | `supabase/migrations/0027_messages.sql` (`thread_open` checks auth + supplier published but no role check; `grant execute ... to authenticated`), `app/api/v1/messages/route.ts` (route enforces buyer/admin only for `action=open`, showing intent mismatch). | As any authenticated supplier, call Supabase RPC `thread_open` directly (bypassing route); thread is created with caller as `buyer_id` and participant role `buyer`. | Add role check inside `thread_open` (buyer/admin only) and keep route check as defense in depth. |
| REZ6-04 | P2 | Public API abuse / middleware | `/api/discover/suggest` is not covered by H2 API rate limiting and has no query-length guard, making DB-backed typeahead abuseable for high-cost traffic spikes. | `lib/rate-limit/limits.ts` (`classifyRoute` only tags `/api/v1/*` as API limited), `middleware.ts` (uses classifier), `app/api/discover/suggest/route.ts` (DB calls on every request, no max `q` length). | Send high-rate requests to `/api/discover/suggest?q=<very long string>` from many IPs; no API read/write limiter bucket applies, each hit can invoke RPC + facet fetch. | Add explicit limiter class for `/api/discover/suggest` and cap `q` length early (e.g., 80-120 chars). |
| REZ6-05 | P3 | Match / auth contract drift | `buyer_smart_match` RPC is granted to `anon`, so buyer-only match logic is callable without authenticated buyer role if invoked directly. | `supabase/migrations/0070_buyer_smart_match_discover_wrapper.sql` (`grant execute ... to anon, authenticated`), `app/api/v1/match/route.ts` (route enforces buyer/admin intent). | Invoke RPC directly with anon client key; receive Smart Match results payload despite product intent of buyer-only wizard. | Restrict RPC execute grant to authenticated (and enforce buyer/admin role in SQL). |
| REZ6-06 | P3 | Admin feedback workflow | Admin feedback status endpoint silently defaults invalid/missing status to `triaged` instead of rejecting bad input, causing accidental state mutation and audit noise. | `app/api/v1/admin/feedback/[id]/route.ts` (`status` initialized `triaged`; invalid input paths keep default and still write). | Submit JSON/form with invalid `status`; record is still updated to `triaged` (mutation happens where caller likely expected validation error). | Validate strictly and return 400 on unknown status; only mutate on explicit valid value. |
