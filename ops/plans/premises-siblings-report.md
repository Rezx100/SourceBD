## 2. Link or merge

**Link.** A shed, extension or unit profile becomes a building of the main company (`facility_of`, migration 0091), which is how 610 rows were already handled. It is not merged, because:

- The safety register lists each building as its own factory, with its own inspection reports, progress and worker count. Read on 13 Oct 2026: Zaheen's main entry is RSC factory 11497 (893 workers, 93% done); the sheds are factory 24449 (1,634 workers, 75% done). A merge puts both on one row and the record can no longer say which building a report belongs to.
- A link survives the nightly re-scrape (the publish guard, 0092), sends the old address to the main company (0096, live) and shows the building on the main record's Facilities panel (0097-0099). A merge deletes the second row.
- A link is undone by clearing one column. A merge is not undone.

The one exception is a pair that holds the **same register entry** on both rows: that is one entry filed twice, and `ops/merge_duplicate_suppliers.py --pair` is the tool.

The August inventory (`ops/plans/rez-58-facility-compliance-inventory.md`) found that gap for memberships; 0099 was written to close it and has not been re-measured here.

A linked row stays linked, but the next new shed the RSC lists would be published the same way until the rule knows the word. A code change with tests, no data.

## 5. Group (c): how the app would learn "no other profile" (a proposal, nothing built)

Whether a qualifier can be dropped depends on the other rows, not on the name: "Unit-2" is noise while the company has one profile and the only thing telling two profiles apart once a second is published. A title is drawn from one row, so the answer has to be stored or looked up.

**Option 1, recommended: a stored display name.** `suppliers.name_display` already exists; it is empty on every row and only the admin pages read it. A re-runnable job (this script's rule) writes the name without its qualifier for group (c), and clears it again when a second profile of that name is published. The buyer pages show it when set, the filed name otherwise; the filed name stays on the record as "Registered name" and the qualifier is listed on the Sites tab, as PR 505 does for buildings. Cost: the two readers that feed search and the record return one more column (one migration), and the job runs after each register load. An admin can overrule any title by hand, which matters for the awkward ones below.

**Option 2: a flag worked out live.** Store each row's base name once and let the readers count other published rows with the same base. Never out of date, but it adds a column, an index and a count to every search row, and nobody can overrule a single title.

Either way the founder also picks **which qualifiers go**. Of the 73: 6 name a building (already cut from titles by PR 505 where bracketed), 34 name a unit or division, and 33 are something else: a filing note ("FOR UD"), an abbreviation ("KSI"), a group or sister-concern line. Recommended: drop buildings and units by rule, and decide the others from the list above, since "(Buying House)" or "(Spinning Mills)" can be the only words saying what the company is.
